ANTARA code audit: sun tracking, detumble pipeline, and relay/comms model issues with fix plans

Issue 1 — Sun tracking

Design intent gapSUN_POINTING does not track the sun

The code comment inside _compute_sun_pointing_attitude is explicit:

def _compute_sun_pointing_attitude(self, orbit_state, sun_visible): """SUN_POINTING is a power-state label, not an active Sun-tracking mode. The spacecraft continues holding the nominal RAM/NADIR/orbit-normal baseline attitude; only the telemetry label changes... """ base_command = self._compute_default_orientation_attitude(orbit_state) return AttitudeCommand( quaternion=base_command.quaternion.copy(), active_attitude_target="DEFAULT_ORIENTATION_HOLD", ← copies default hold attitude_hold_reason="Nominal inertial hold retained; " "SUN_POINTING is not an attitude-tracking mode", )
The spacecraft never rotates +Z toward the Sun. In SUN_POINTING the attitude is identical to the DEFAULT_ORIENTATION_HOLD: +X=RAM, +Y=nadir, +Z=orbit-normal. Solar generation relies entirely on the coincidental alignment of the +Z panel with the sun incidence angle — which only works well at high beta angles like β≈78° in this sim.
At low beta angles (β<40°) the +Z panel would face nearly edge-on for large fractions of each orbit, dramatically cutting power. The sim hides this because β is locked at 78° (epoch 2000-03-01, inclination 97.6°, RAAN 60°).
The solar model correctly reads the actual sun incidence angle via _compute_sun_incidence_angle_deg using the dot product of +Z body axis vs sun vector. So the EPS model is not lying — it just happens that at β≈78° the +Z panel is always near-normal to the sun during the inertial hold.

Is this a bug? Only if the mission requires active sun tracking. The ICD comment says +Z is the fixed solar panel. If +Z is body-fixed (no articulation), then orienting the whole body toward the sun conflicts with the RAM-face requirement for science. The code's philosophy is deliberate but must be documented as a design choice, and a low-beta risk analysis must be added.

Fix plan
1
Add a dedicated _compute_sun_tracking_attitude that aligns +Z to the sun vector using build_frame("+Z", sun_unit, "+X", velocity_unit) — symmetric to how RELAY builds the +Y frame.
2
Gate it on a new config flag sun_tracking_enabled: bool = False. When True, SUN_POINTING enters a slew cycle to keep +Z within startup_sun_incidence_deg (currently 75°) of the sun. When False, current behavior is preserved (inertial hold).
3
Add a beta-angle monitor: if β<50°, log a warning that the passive inertial hold may produce <60% of peak solar power and trigger sun tracking automatically.
4
In the EPS summary, report the actual minimum and maximum solar generation per orbit (not just the average) so low-incidence periods show up in the report.
Issue 2 — Detumble pipeline

Logic gapFive specific vulnerabilities found

Vulnerability A — FSM can exit DETUMBLE without physics completing

FSM.evaluate(): if self.current_mode == "DETUMBLE": if detumble_complete: return "SUN_POINTING", "Physics detumble complete" return self.current_mode, "Remain in detumble startup" _step_detumble_physics(): self.fsm.detumble_complete = self.adcs.detumble_complete ← set here run() loop ordering: 1. fsm.evaluate() ← reads detumble_complete BEFORE physics step 2. _update_attitude_guidance() → _step_detumble_physics() ← sets it HERE 3. fsm.transition() ← acts on result of step 1
The FSM evaluates detumble_complete BEFORE _step_detumble_physics runs in the same timestep. This means the flag is always one step stale. In the worst case the spacecraft exits DETUMBLE one step before physics truly converges, leaving a small residual body rate that enters SUN_POINTING uncorrected.

Vulnerability B — No timer backstop for DETUMBLE

startup_detumble_sec: float = 1000.0 ← configured but NEVER USED in FSM.evaluate()
The 1000s detumble timer exists in MissionConfig but SpacecraftFSM.evaluate() only checks the physics flag. If B-dot torque is insufficient (weak B-field geometry, noisy sensor), the spacecraft stays in DETUMBLE forever with no watchdog exit.

Vulnerability C — detumble_complete desync between ADCSModel and FSM

ADCSModel.step_detumble(): self.detumble_complete = True ← set on ADCS _step_detumble_physics(): self.fsm.detumble_complete = self.adcs.detumble_complete ← synced here _complete_detumble_phase(): self.fsm.detumble_complete = self.adcs.detumble_complete ← also set here FSM.evaluate(): if detumble_complete: ... ← reads the arg passed in from run() run(): self.fsm.evaluate(..., self.adcs.detumble_complete, ...) ← from ADCS directly
Three separate code paths write to detumble_complete on the FSM (the physics step, _complete_detumble_phase, and the FSM's own detumble_complete field). The FSM evaluate also receives the flag as an argument from the run loop bypassing the FSM field. This creates three potential sources of truth — any divergence means silent wrong behavior.

Vulnerability D — WHEEL_DAMP phase starts before B-dot settles

step_detumble(): max_rate = max(abs(body_rate_deg_sec)) if self.detumble_phase == "BDOT" and max_rate <= bdot_handover_rate_deg_sec: self.detumble_phase = "WHEEL_DAMP" ← switches on ONE step below threshold bdot_control(): bdot_t_sec = (b_body_t - last_b_body_t) / dt_sec ← finite difference desired_m = -gain * bdot_t_sec
The BDOT→WHEEL_DAMP handover fires on the first timestep the rate drops below threshold. A single noisy dB/dt reading could push rate below threshold momentarily. A 3-step hysteresis counter (rate must stay below threshold for N consecutive steps) would make this robust.

Vulnerability E — Zero-quaternion risk during detumble

_integrate_quaternion_from_body_rates(): omega_mag = norm(omega_deg_sec) if omega_mag <= 0.0 or dt_sec <= 0.0: self._update_quaternion_tuple() return ← safe early exit axis_unit = omega_deg_sec / omega_mag ← division is safe here ADCSModel.set_initial_quaternion(): norm = linalg.norm(quaternion) if norm <= 0.0: raise ValueError("Cannot normalise a zero quaternion.") ← explicit guard
The quaternion integration has correct zero-rate guards and the normalization path has an explicit error. No zero-quaternion vulnerability found in the physics path.
Fix plan
A
Move _step_detumble_physics() (and the self.fsm.detumble_complete sync) to BEFORE fsm.evaluate() in the run loop. Alternatively, evaluate detumble exit on the next step (read the flag set by the previous step's physics). Either ordering must be documented in the loop header.
B
In FSM.evaluate() for the DETUMBLE branch, add a timer watchdog: if self.time_sec - self.mode_entry_time_sec > config.startup_detumble_sec: return "SUN_POINTING", "Detumble watchdog timeout". Also log a warning if exiting via watchdog rather than physics convergence.
C
Make detumble_complete a single source of truth on ADCSModel. Remove the copy on FSM. The run loop passes self.adcs.detumble_complete to fsm.evaluate() as the authoritative value. Delete self.fsm.detumble_complete assignments in _step_detumble_physics and _complete_detumble_phase.
D
Add self._bdot_below_threshold_count: int = 0 to ADCSModel. In step_detumble(), increment on each step below threshold, reset on any step above. Only handover to WHEEL_DAMP when count ≥ 3 (equivalent to 6s at 2s timestep).
E
Add a post-detumble attitude check in _complete_detumble_phase: verify norm(body_rate_deg_sec) < detumble_stable_rate_deg_sec * 2 before accepting the exit. If not, re-enter BDOT for one more damping cycle.
Issue 3 — Comms model & relay logic

Critical failureRelay pointing gate blocks all downlink

The downlink activation is gated by six conditions evaluated in sequence in the run loop. Tracing them in order:

relay_link_active = ( current_mode == "RELAY" ✓ mode transitions work and gs_visible ✓ GS geometry correct and relay_settled ✓ settling time short (10s) and self.science_storage_mb > 0.0 ✗ ALWAYS ZERO — see Bug A below and relay_pointing_valid ✗ ALWAYS FALSE — see Bug B below and gs_off_boresight_deg <= 40.0 ✗ BLOCKED BY Bug B )

Bug A — Science storage is always zero during RELAY contacts

ANTARAScienceSimulator.__init__(): self.science_storage_mb = 0.0 ← starts at zero _update_storage(): self.science_storage_mb = min(capacity, max(0, science_storage_mb + generated - downlinked)) downlink_step(): requested_mb = downlink_rate_mbps * dt_sec / 8.0 downlinked_mb = min(storage_mb, requested_mb) ← uses science_storage_mb arg relay_link_active condition: self.science_storage_mb > 0.0 ← checks science_storage_mb Mission timeline from output: T+0.00–7.30 hr : SUN_POINTING, no science T+7.30–7.40 hr : DETECTION (0.011 MB generated) ← science IS generated T+12.95 hr : RELAY contact (GS visible) science_storage_mb at T+12.95 hr : 0.011 MB ← should be >0
Science storage IS non-zero at RELAY time (0.011 MB from DETECTION at T+7.30). Bug A is NOT the root blocker — the storage check should pass for contacts after the first DETECTION pass. The output's 0.00 MB downlink points squarely at Bug B.

Bug B — Relay attitude is frozen at the wrong quaternion (ROOT CAUSE)

_compute_relay_attitude(): if (self.current_attitude_command is not None and self.current_attitude_command.active_attitude_target == "RELAY_INERTIAL_HOLD"): return AttitudeCommand( quaternion=self.adcs.target_quaternion.copy(), ← returns STALE quaternion active_attitude_target="RELAY_INERTIAL_HOLD", ) ← HOLDS without re-solving GS vector return self._compute_relay_candidate(orbit_state, target_unit) _compute_relay_candidate(): quaternion = self.build_frame("+Y", target_unit, "+Z", z_reference) # builds correct attitude — BUT this branch only runs on MODE ENTRY # After entry, the inertial hold is frozen indefinitely
The relay attitude is computed ONCE at mode entry using the GS LOS vector at that instant, then frozen as an inertial hold. The GS moves relative to the spacecraft at roughly 1–2°/s during a pass. Within 30–60 seconds the +Y relay antenna has drifted well outside the 10° validity threshold and the 40° beamwidth. The simulation confirms this: the first RELAY entry fires a warning at T+0.70 hr ("relay pointing error exceeded 90 deg") within ONE or TWO timesteps of entry, meaning the initial quaternion itself was wrong.

Bug C — Relay slew direction diverges from GS position

_begin_slew_transition(): target_command = self._get_attitude_command(target_mode, orbit_state, ...) # calls _compute_relay_attitude → _compute_relay_candidate at slew START # slew takes slew_transition_penalty_sec = 60s minimum # GS moves ~1-2 deg/s during slew; by slew END the GS has moved ~60-120 deg # in the worst case (low-elevation short pass) the pass is already over _compute_relay_candidate(): target_unit = _ground_station_vector_unit(orbit_state) ← GS position at slew START
The slew target is frozen at the GS position when the slew begins. For a 60s penalty + slew time, and a GS that moves 1°/s, the target is 60° stale by slew completion. A short pass (4–5 min) can lose 25% of its window to this stale slew.

Bug D — Relay pointing validity threshold is geometrically impossible after inertial freeze

config: relay_pointing_valid_deg: float = 10.0 ← validity threshold _compute_relay_attitude(): returns inertial hold → +Y drifts w.r.t. GS relay_pointing_error grows at ~1-2 deg/s → exceeds 10 deg in 5-10 seconds after RELAY entry relay_link_active gate: relay_pointing_valid = relay_pointing_error <= 10.0 ← NEVER satisfied
The 10° threshold is physically impossible to maintain without active GS tracking. Either the threshold must be raised to match the beamwidth (40°), or active closed-loop tracking must be added in RELAY mode.

Bug E — CommunicationsModel has no link budget model

CommunicationsModel.downlink_step(): requested_mb = config.downlink_rate_mbps * dt_sec / 8.0 ← fixed 9.6 kbps always downlinked_mb = min(storage_mb, requested_mb) # No elevation-angle margin, no path loss, no SNR model # No degradation at low elevation angles # No EIRP or G/T parameters
The comms model assumes constant 9.6 kbps regardless of elevation angle. In reality, a 15° elevation contact has 6–8 dB more path loss than a zenith pass. For a PDR this is acceptable but must be upgraded before CDR.
Fix plan — in priority order
1
Active GS tracking in RELAY: Remove the inertial-hold branch in _compute_relay_attitude. Instead, re-solve the GS LOS vector every timestep and call adcs.command_attitude() with the updated quaternion and the relay_track_deadband_deg (2°) as the deadband. This gives continuous closed-loop GS tracking throughout the pass.
2
Predictive slew targeting: In _begin_slew_transition for RELAY, propagate the GS LOS vector forward by duration_sec using the current orbital velocity to estimate the GS position at slew completion. Use that predicted position as the slew target quaternion rather than the current instantaneous position.
3
Raise or remove relay_pointing_valid_deg gate: With active tracking, the sustained pointing error should stay within 2–5°. Keep the gate but lower threshold to 5° (still strict, but achievable). Without active tracking, raise to 35° to match the beamwidth minus margin.
4
Add elevation-dependent link rate to CommunicationsModel: effective_rate = base_rate * max(0, sin(elevation_deg)^0.5) is a simple approximation. Proper fix is a Friis link budget: EIRP − path_loss(d) − atmospheric_loss + G/T → Eb/N0 → Shannon rate. Add gs_elevation_deg as a parameter to downlink_step().
5
Add AOS prediction and pre-slewing: Track the next GS AOS time from the previous LOS. Begin the RELAY slew one slew_transition_penalty_sec before predicted AOS so the antenna is already pointed at the GS when the contact window opens.
6
Add a second ground station: GS_INDIA is at lat=15°, lon=74°. With a 97.6° inclination, many descending passes cross longitudes well east or west of 74°E. Adding a polar/high-latitude station (e.g., Svalbard at 78°N) or an equatorial station at lon=−60° (Brazil) would triple contact opportunities. Also fix gs_elevation_mask_deg — it is 15° in is_visible() but the docstring says 10°.
